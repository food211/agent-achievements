# 分阶段诊断流程

这套流程诊断的是创作者与 Code Agent 之间积累的规则和工作流，不诊断文本作品，也不分析人的五行。Agent 是审计者和整理者，人是最后的判断者；不要把“找出陈旧规则”的工作变成一份让用户填写的问卷。

## 节奏

- 每一步都先完成 `current_question.prework`，用 `coach-observe` 保存 Agent 已经完成的分析，再展示结果和一个最小决策口。没有分析结果，不得抛出问题。
- 一次只处理 `current_question.prompt` 对应的判断目标，但不要把提示词原句当成不可改变的台词。
- 每次 `coach-status` 都会返回 `inventory_context`。恢复旧会话时先用它确认当前问题所指的规则范围；不要让用户重新列一遍，也不要把整份清单再次倾倒到对话里。
- 用户回答后，判断是否已经做出明确取舍、纠正了某项事实，或补充了 Agent 无法读取的原始意图。满足其中一项即可记为 `quality: concrete`。
- 如果用户只说“应该有”“一般来说”“可能是审美问题”，以 `quality: needs_followup` 保存并停留在当前步骤。Agent 继续查证、缩小候选或做对比，再给一个更容易判断的选择；不要把“请再举个实例”原样推回用户。
- Agent 负责回答“已经沉淀了什么、哪里有失效信号、当前机制怎样运行、建议如何处理”；用户只回答“这是否符合我的原始意图、批准哪一种取舍”。
- 等待用户回答时，只挂起这次访谈；其他独立开发任务可以继续。
- Agent 在真实任务中遇到判断不了的问题时，立即用 `issue-log` 写入本地数据库；用户给出取舍后，用 `decision-log` 保存用户原话、理由和处理方式。不要只把这些信息留在聊天记录。

## 三段顺序

1. `creator`：先扫描并确认已经沉淀的做法，再由 Agent 找出陈旧候选、追查保护目的、归纳人必须亲自判断的边界。用户不负责从零举例。
2. `technical`：Agent 先从已确认实例拟出“什么必须留给人”，再回放什么不入队和筛错的后果；用户负责批准或修正，不负责设计整套系统。
3. `boundary`：明确不做项、不成立的五行映射和实现依赖。映射卡住时原样记录为 `unmapped`，不要替框架圆过去。

## 第一问的正确形态

不要问：

> 你已经沉淀了哪些固定做法？请举一个例子。

先扫描并展示，例如：

| 类型 | 找到的沉淀 | 来源 | 当前用途 |
|---|---|---|---|
| Skill | git-recap | `skills/git-recap/SKILL.md` | 提交后生成结构化回顾 |
| Rule | 数据完整性约束 | `AGENTS.md` | 限制高风险数据写入 |

然后只问：

> 这是我找到的完整清单。哪些已经停用、描述不准或遗漏？如果准确，回复“清单准确”即可。

清单中的一项必须是用户能够单独保留、修改或退役的真实对象，例如一个 Skill、一个规则文件，或文件中有明确边界的一条规则。每项必须带实际路径和当前用途。

不要把以下内容冒充清单项：

- 从长文档中概括出的“产品与数据规则”“工程流程规则”等抽象大类；
- 没有独立来源文件的运行时话题或能力描述；
- 只是模板内容、产品功能或代码模块，但并不约束 Agent 行为的东西；
- 同一个规则文件拆出的几十个主题词。

规则很多时，完整结果保存在 `inventory_context`，给人先展示按来源计数的索引和最值得辨认的 5 项。用户要求“继续”再翻下一组，不一次铺满屏幕。

从第二步开始，Agent 先提交候选、证据或建议，再让用户做最小判断。用户要求重新列对象、排序、过滤、比较或补证据时，立即改变呈现方法，但仍停留在同一个判断目标。

## 让用户改造提问方式

`current_question.prompt` 规定要问清什么，不规定只能怎样问。用户对提问方式的修正优先于预设话术，并在本步骤余下对话中持续生效。

真实用法：

1. Agent 问“有没有过时但仍在用的规则？请讲一个实例”。
2. 用户说“把它们列出来给我看看”——把开放回忆题改成候选识别题。
3. 用户再说“把修改时间最早的 Top 5 给我”——沿用用户选择的筛选轴，把候选缩到可判断范围。
4. Agent 展示结果后问“这 5 条里，哪一条让你想起了实际失效经历？都没有也可以。”不要重复最初那句开放问题。

执行规则：

1. 不调用 `coach-answer`，不移动步骤。
2. 从 `inventory_context` 取真实对象，按用户指定的方式重组；每次最多展示 5 项，列出名称、精确路径、当前用途和所用筛选依据。
3. 用 `coach-observe` 把这次辅助清单保存到当前 `step_id`。后续 `coach-status` 会通过 `support_context` 带回它，换 Agent 或恢复会话后也继续使用已经调整过的问法。
4. 如果用户按 Git 时间排序，写清是文件最后一次可见修改时间。时间只用于缩小选择范围，不能作为规则已经过时、仍在使用或应当退役的证据。
5. 用户没有指定筛选方式时，可以给出两三个简单选项，例如“按最近人工纠正 / 按代码冲突 / 按最后修改时间”，让用户选择；不要自行发明可疑度。
6. 展示后用选择题或对比题继续同一个判断，例如“这 5 条里哪条有过失效经历？都没有也可以”。不要退回原来的开放式问法，也不要顺势跳到下一问。

示例：

| 对象 | 来源 | 当前用途 | 辅助信息 |
|---|---|---|---|
| `browser-testing` | `.agents/skills/browser-testing/SKILL.md` | 规定何时做浏览器验收 | 最近修改：2026-06-01 |

不要只报文件名和提交哈希；用户需要知道这条东西现在约束什么，才有可能判断它是否过时。

## 提问口径

- 第一段要让用户以“开发创作者”的身份回答，先忘掉实现。
- 第二段才切换到技术，而且把入队判据当作最重要的问题，不急着往后走。
- 第三段只划边界，不趁机扩展路线图。
- 不一次抛出整份问卷，不替用户总结出一个漂亮答案后让她点头。
- 不把用户为了理解问题而提出的列表、排序、解释请求记成访谈答案；把它们视为对提问方法的明确修正并立即沿用。
- 证据不足时，Agent 优先补查：哪条规则或哪次任务、发生了什么、谁发现的、之后怎么处理。只有原始意图确实不在仓库和历史里时，才向用户补一个最小缺口。

## 完成条件

状态成为 `ready_to_synthesize` 后，结合访谈答案与可核验的代码证据输出：

1. 一个能跑的最小闭环设计；
2. “什么该留给人”的一个具体判据；
3. 明确的不做清单。

这时才能把达到证据门槛的问题写成 finding。访谈答案本身不是规则失效的充分证据。

## 判断数据库

`.wuxing-harness/harness.db` 是事实记录，包含：

- `issues`：Agent 遇到的具体问题、影响范围、可逆性、是否正在等人，以及用于识别同类问题的 `fingerprint`；
- `human_decisions`：用户对某个问题的原话决定、理由，以及询问、自行处理、继续观察、创建/替换/退役规则中的一种处置；
- `coaching_answers`：分阶段访谈的逐步回答，用于跨会话恢复和最终综合。
- `coaching_observations`：保存第一步扫描到的真实规则对象、路径与证据，后续通过 `inventory_context` 继续引用。

同一个 `fingerprint` 的出现次数可以作为“是否反复发生”的证据，但次数本身不自动创建规则。只有找到共通点并达到审查证据门槛，才提出规则修改。

预调查输入遵守 [coaching-observation.schema.json](coaching-observation.schema.json)，问题输入遵守 [issue.schema.json](issue.schema.json)，人的决策输入遵守 [decision.schema.json](decision.schema.json)。`fingerprint` 应描述可复用的情形（例如“无明确产品规则时批量补齐历史数据”），不要用当前文件名或随机任务 ID 造成同类问题无法聚合。用 `history` 读取已有记录和同类出现次数；不要直接拼 SQL。
