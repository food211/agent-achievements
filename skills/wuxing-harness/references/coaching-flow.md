# 分阶段诊断流程

这套流程诊断的是创作者与 Code Agent 之间积累的规则和工作流，不诊断文本作品，也不分析人的五行。

## 节奏

- 每轮只问 CLI 返回的 `current_question`，不要提前展示后续问题。
- 用户回答后，先判断它是否包含真实发生过的规则、任务或判断。只有具体答案才以 `quality: concrete` 前进。
- “应该有”“一般来说”“可能是审美问题”这类回答以 `quality: needs_followup` 保存，并在同一步只追问一个具体实例。
- 不要因为已经扫描了代码就替用户回答产品判断。代码证据用于核对实例，不替代创作者的取舍。
- 等待用户回答时，只挂起这次访谈；其他独立开发任务可以继续。
- Agent 在真实任务中遇到判断不了的问题时，立即用 `issue-log` 写入本地数据库；用户给出取舍后，用 `decision-log` 保存用户原话、理由和处理方式。不要只把这些信息留在聊天记录。

## 三段顺序

1. `creator`：先理解已经沉淀的做法、过时或失去目的的规则，以及人必须亲自判断的真实时刻。未得到具体实例，不进入技术段。
2. `technical`：先定“什么必须留给人”，再讨论非阻塞续跑、规则沉淀、规则推翻和三个证据数字。不要先画架构再补入队判据。
3. `boundary`：明确不做项、不成立的五行映射和实现依赖。映射卡住时原样记录为 `unmapped`，不要替框架圆过去。

## 完成条件

状态成为 `ready_to_synthesize` 后，结合访谈答案与可核验的代码证据输出：

1. 一个能跑的最小闭环设计；
2. “什么该留给人”的一个具体判据；
3. 明确的不做清单。

这时才能把达到证据门槛的问题写成 finding。访谈答案本身不是规则失效的充分证据。

## 判断数据库

`.wuxing-harness/harness.db` 是事实记录，包含：

- `issues`：Agent 遇到的具体问题、影响范围、可逆性、是否正在等人，以及用于识别同类问题的 `fingerprint`；
- `human_decisions`：用户对某个问题的原话决定、理由，以及询问、自行处理、继续观察、创建/替换/退役规则中的一种处置；
- `coaching_answers`：分阶段访谈的逐步回答，用于跨会话恢复和最终综合。

同一个 `fingerprint` 的出现次数可以作为“是否反复发生”的证据，但次数本身不自动创建规则。只有找到共通点并达到审查证据门槛，才提出规则修改。

问题输入遵守 [issue.schema.json](issue.schema.json)，人的决策输入遵守 [decision.schema.json](decision.schema.json)。`fingerprint` 应描述可复用的情形（例如“无明确产品规则时批量补齐历史数据”），不要用当前文件名或随机任务 ID 造成同类问题无法聚合。用 `history` 读取已有记录和同类出现次数；不要直接拼 SQL。
