# 分阶段诊断流程

这套流程诊断的是创作者与 Code Agent 之间积累的规则和工作流，不诊断文本作品，也不分析人的五行。

## 节奏

- 每轮先完成 CLI 返回的 `current_question.prework`，用 `coach-observe` 保存并向用户展示候选清单；没有预调查，不得提问。
- 用户不负责提供 Agent 能读取的事实。让用户确认、纠正、排除候选或选择优先项，不要让她从空白开始罗列规则、代码能力、指标或依赖。
- 用户回答后，判断它是否落在已展示的真实规则、任务或判断上。确认一份带证据的候选清单也算 `quality: concrete`。
- 如果用户给出“应该有”“一般来说”“可能是审美问题”这类模糊判断，先自行继续查证；只有仓库、历史和判断数据库都无法补足时，才以 `quality: needs_followup` 保存并询问一个最小缺口。
- 扫描结果负责回答“现在有什么、代码怎样运行、过去发生过什么”；用户只负责“是否符合意图、应该保留哪种取舍”。不要用代码替用户做产品判断，也不要把代码能回答的问题推回用户。
- 等待用户回答时，只挂起这次访谈；其他独立开发任务可以继续。
- Agent 在真实任务中遇到判断不了的问题时，立即用 `issue-log` 写入本地数据库；用户给出取舍后，用 `decision-log` 保存用户原话、理由和处理方式。不要只把这些信息留在聊天记录。

## 三段顺序

1. `creator`：先理解已经沉淀的做法、过时或失去目的的规则，以及人必须亲自判断的真实时刻。未得到具体实例，不进入技术段。
2. `technical`：先定“什么必须留给人”，再讨论非阻塞续跑、规则沉淀、规则推翻和三个证据数字。不要先画架构再补入队判据。
3. `boundary`：明确不做项、不成立的五行映射和实现依赖。映射卡住时原样记录为 `unmapped`，不要替框架圆过去。

## 第一问的正确形态

不要问：

> 你已经沉淀了哪些固定做法？请举一个例子。

先扫描并展示，例如：

| 类型 | 找到的沉淀 | 来源 | 当前用途 |
|---|---|---|---|
| Skill | git-recap | `skills/git-recap/SKILL.md` | 提交后生成结构化回顾 |
| Rule | 数据完整性约束 | `AGENTS.md` | 限制高风险数据写入 |

然后只问：

> 这是我找到的完整清单。哪些已经停用、描述不准或遗漏？如果准确，回复“清单准确”即可。

后续每一步都遵守同一结构：`扫描结果 → 证据 → Agent 的候选判断 → 用户最小决策`。

## 完成条件

状态成为 `ready_to_synthesize` 后，结合访谈答案与可核验的代码证据输出：

1. 一个能跑的最小闭环设计；
2. “什么该留给人”的一个具体判据；
3. 明确的不做清单。

这时才能把达到证据门槛的问题写成 finding。访谈答案本身不是规则失效的充分证据。

## 判断数据库

`.wuxing-harness/harness.db` 是事实记录，包含：

- `issues`：Agent 遇到的具体问题、影响范围、可逆性、是否正在等人，以及用于识别同类问题的 `fingerprint`；
- `human_decisions`：用户对某个问题的原话决定、理由，以及询问、自行处理、继续观察、创建/替换/退役规则中的一种处置；
- `coaching_answers`：分阶段访谈的逐步回答，用于跨会话恢复和最终综合。
- `coaching_observations`：Agent 每一步提问前扫描到的候选、路径与证据，保证用户不是从零作答。

同一个 `fingerprint` 的出现次数可以作为“是否反复发生”的证据，但次数本身不自动创建规则。只有找到共通点并达到审查证据门槛，才提出规则修改。

预调查输入遵守 [coaching-observation.schema.json](coaching-observation.schema.json)，问题输入遵守 [issue.schema.json](issue.schema.json)，人的决策输入遵守 [decision.schema.json](decision.schema.json)。`fingerprint` 应描述可复用的情形（例如“无明确产品规则时批量补齐历史数据”），不要用当前文件名或随机任务 ID 造成同类问题无法聚合。用 `history` 读取已有记录和同类出现次数；不要直接拼 SQL。
